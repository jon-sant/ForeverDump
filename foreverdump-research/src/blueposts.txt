[https://discord.com/channels/327414731654692866/1473839027018010826 {{apisummary.title|Midnight 12.0.1 AddOn Restrictions Update}}]
<blockquote {{apisummary.blizzquote}}>
Hello again from Blizzard! We have a small list of changes that are being hotfixed to live in preparation for Early Access launch next week. You should expect these to hit live servers in the next few days.
DISCLAIMER: These notes are for addon authors and as such are focused specifically on addon security changes only. Changes planned for other parts of the game (UI or otherwise) are not included here.
NOTE: While most of these are bugfixes that last couple changes were made to address exploits or addon functionality we did not want to allow. Apologies for the late changes there!
</blockquote>
<details open>
{{apisummary.header|Changes due to be deployed before Midnight Early Access}}
*Fixed an exploit that allowed addons to declassify spell names using tricky string formatting. APIs no longer accept secret spell names from addons as a result. (Already live)
*Fixed an exploit where status bars could be used to launder secret numbers.
*Fixed an issue where calling {{api|debuglocals}} after certain Lua errors would cause a crash.
*Fixed an issue where numerous APIs that accept aura instance IDs would stop working after a full aura update (relog was the easiest repro).
*Fixed an issue where enabling timestamps on chat frames would cause Lua errors when chat lockdowns are in effect.
*Threat APIs now conditionally return secrets for some combinations of input unit tokens to prevent unintended use of these functions to compare units.
*Various APIs no longer accept compound unit tokens or unit names when in an active PvP match.
Bonus notes that were forgotten:
Fixed an exploit that allowed addons to access spell IDs and durations of crowd control effects for other players.
Fixed an exploit that allowed addons to access cooldowns of PvP trinkets for other players in arenas.
</details><br>
===2026-02-24===
[https://discord.com/channels/327414731654692866/1475979247825977595 {{apisummary.title|Midnight 12.0.1 Spell Declassification Update}}]
<blockquote {{apisummary.blizzquote}}>
Hello again from Blizzard!
Today we have an update regarding which spells we are going to be flagging as non-secret for Midnight launch. These changes are planned to go out in a data hotfix in the next couple days, but we wanted to give you all a heads up beforehand so you can plan any necessary changes to your addons.
Over the course of Beta, as well as recent weeks on live, one of the biggest recurring points of feedback has been from healers who wish that our default UI provided more robust options for filtering or emphasizing specific buffs on raid frames. In the past month we have added a few layers of extra logic to buff sorting and visibility, and while we've heard positive feedback from many healers about these improvements, we realize that our solutions are leaving others still wanting more customization. 
While we had originally hoped to be able to deliver a streamlined default experience, it has become clear that there are common use-cases that a single set of logic cannot cover. Some players may want to make simple tweaks like highlighting the target of their Preservation Evoker's Echo, or their Holy Paladin's active Beacon, while others would consider that to be distracting clutter. We are now beginning work on a system to allow players to hide or emphasize buffs from their spellcasts on a per-spell basis, via the Spellbook. We expect that solution to be ready for players in a later Midnight patch.
In the meantime, we have also seen a few addons popping up that use non-secret information to make very reliable guesses about players' spellcasts in order to drive this sort of filtering logic. Breaking the API calls driving this functionality would cause significant collateral damage to common addons, and we are not planning to do go down that path. Ultimately, this design space is mostly about customizing the display of information, rather than objectively advantageous computational solutions, so we want to treat it the same way we approached resources like Holy Power or Maelstrom.
Thus, rather than requiring addon developers to jump through hoops to support an implementation that will have some frustrating inaccuracies, we are planning to flag a number of short-cooldown rotational healer spells, and very long duration buffs, to exclude them from our Secret Value system. We will likely re-protect these spells once our own filtering solution, with its own addon hooks for display customization, is in place.
The full list of spells being flagged is below, broken down into several categories.
</blockquote>

===2026-03-21===
[https://discord.com/channels/327414731654692866/1484980480217448540 {{apisummary.title|Midnight 12.0.1 Upcoming Restriction Changes}}]
<blockquote {{apisummary.blizzquote}}>
Hello again from Blizzard! Mythic raids and M+ open this week and we will be hotfixing in some last-minute changes to fix exploits before resets.
We recognize that some of these changes are going to be disruptive and require last-second changes to your addons, and we sincerely apologize for them coming in so late. Part of these changes involve removing the secure delegate portion of ActionButton_ApplyCooldown. We have added new APIs that should replace the functionality it provided, but we will be watching closely for reports of functionality that still needs replacing.
DISCLAIMER: These notes are for addon authors and as such are focused specifically on addon security changes only. Changes planned for other parts of the game (UI or otherwise) are not included here.
</blockquote>
<details open>
{{apisummary.header|Cooldowns}}
* Removed the ability for tainted code to configure cooldown frames with secret values via {{api|t=w|Cooldown:SetCooldown|SetCooldown}}, {{api|t=w|Cooldown:SetCooldownFromExpirationTime|SetCooldownFromExpirationTime}}, {{api|t=w|Cooldown:SetCooldownDuration|SetCooldownDuration}}, and {{api|t=w|Cooldown:SetCooldownUNIX|SetCooldownUNIX}}.
** This does not impact {{api|t=w|Cooldown:SetCooldownFromDurationObject|SetCooldownFromDurationObject}} which, going forward, is the only way to configure a cooldown frame with secret values.
* The {{tlygo|ActionButton_ApplyCooldown}} Lua function no longer routes through a secure delegate.
** This unfortunately means that existing code passing secrets into this function will start throwing Lua errors when the hotfix goes live. However, all of the logic that this function is doing should be able to be replicated by addons with the new <code>isActive</code>/<code>shouldReplaceNormalCooldown</code> boolean fields and duration objects (see below for details on those).
* Action/Spell cooldown APIs now return <code>isEnabled</code> and <code>maxCharges</code> as non-secrets.
* Action/Spell cooldown APIs now return a new non-secret <code>isActive</code> boolean, which is set to true if the UI should render a cooldown display.
** For regular cooldowns, it's true if <code>isEnabled and startTime > 0 and duration > 0</code>.
** For charge cooldowns, it's true if <code>maxCharges > 1 and currentCharges < maxCharges and startTime > 0 and duration > 0</code>.
** For LoC cooldowns, it's true if <code>startTime > 0 and duration > 0</code>.
* Action/Spell cooldown APIs that yield duration objects now return a zero-span object if the <code>isActive</code> boolean evaluates to false.
* Action/Spell cooldown APIs now return results modified by the presence of cooldown aura spells on the player.
** For example, if an action button is assigned to a PvP trinket (Sigil of Adaptation) that has a passive effect of automatically removing a loss of control effect with a 1 minute cooldown, the GetActionCooldown API will track that 1 minute cooldown when the Adaptation debuff has been applied to the player.
** This means no addon code needs to deal with the {{api|C_UnitAuras.GetCooldownAuraBySpellID}} API.
</details>
<details open>
{{apisummary.header|Cooldowns (continued)}}
* Action/Spell Loss of Control cooldown APIs now return a structured table instead of unpacked values.
** These functions have been renamed with an "Info" suffix (eg. {{api|C_Spell.GetSpellLossOfControlCooldownInfo|GetSpellLossOfControlCooldownInfo}}) with a deprecation for the old name that unpacks the start time and duration value.
** This structured table contains several new fields not present in the old API. In addition to the <code>isActive</code> boolean mentioned above, it includes <code>modRate</code> (secret) and <code>shouldReplaceNormalCooldown</code> (non-secret), which is true if the loss of control cooldown has an expiration time that's later than any regular cooldown for this ability/spell.
* Added a new {{api|C_LossOfControl.GetActiveLossOfControlDuration(unitToken, index)}} API that returns a duration object.
* Added a new {{api|GetTotemDuration(slot)}} API that returns a duration object.
</details>
<details open>
{{apisummary.header|Other changes}}
* A change that we had already made in 12.0.5 to restrict the ability to use <code>%.1s</code> style precision specifiers with secret string inputs has been brought forward to 12.0.1.
** As a result, {{api.inline|format("%.1s", secretwrap("Jar Jar Binks"))}} will no longer truncate to "J".
* The {{api|UnitCreatureID}} API now returns nil when unit identity is secret.
* The following script object methods now return nil if relevant secret aspects are assigned: {{api|t=w|Frame:GetEffectiveAlpha()}}, {{api|t=w|StatusBar:IsStatusBarDesaturated()}}, {{api|t=w|Texture:IsDesatured()}}
* Resolved a few issues where {{api.system|TooltipInfo|C_TooltipInfo}} APIs for unit auras had inconsistent security requirements.
* The use of [[MACRO worldmarker|/wm]] and [[MACRO clearworldmarker|/cwm]] in macros has been limited to 3 per second.
Macros are no longer allowed to send BNet whispers while an encounter is active.
* The following  {{api.system|UnitAuras|C_UnitAuras}} APIs can no longer be called while the player is in combat: {{api|C_UnitAuras.AddPrivateAuraAnchor|AddPrivateAuraAnchor}}, {{api|C_UnitAuras.RemovePrivateAuraAnchor|RemovePrivateAuraAnchor}}, {{api|C_UnitAuras.SetPrivateWarningTextAnchor|SetPrivateWarningTextAnchor}}, {{api|C_UnitAuras.AddPrivateAuraAppliedSound|AddPrivateAuraAppliedSound}}, {{api|C_UnitAuras.RemovePrivateAuraAppliedSound|RemovePrivateAuraAppliedSound}}.
</details>

===2026-03-12===
[https://discord.com/channels/327414731654692866/1481702172319027331 {{apisummary.title|Midnight 12.0.5 PTR Changes Episode 1: The Secret Menace}}]
<blockquote {{apisummary.blizzquote}}>
Hello again from Blizzard! With 12.0.5 PTR slated to start today, here is the list of addon API changes you can expect to see in next couple builds, followed by a discussion about some longer-term changes we are considering for the aura system.
DISCLAIMER: These notes are for addon authors and as such are focused specifically on addon security changes only. Changes planned for other parts of the game (UI or otherwise) are not included here.
</blockquote>
<details open>
{{apisummary.header|Coming in 12.0.5 PTR 1}}
{{text|blizz|Numeric Formatting}}
*We have added three new Lua object types for numeric formatting: {{api|t=sc|AbbreviatedNumberFormatter}}, {{api|t=sc|NumericRuleFormatter}}, and {{api|t=sc|SecondsFormatter}}. These types can be supplied with secret numbers through the Format functions on duration objects.
*We're considering adjusting the various "display count" APIs (eg. {{api|C_Spell.GetSpellDisplayCount|GetSpellDisplayCount}}) to accept formatter objects, but this would be a breaking change (let us know your thoughts).
{{text|blizz|Spell & Item Charge APIs}}
*The following APIs will now return a zero-span duration object when the queried spell is at maximum charges: {{api|C_SpellBook.GetSpellBookItemChargeDuration|GetSpellBookItemChargeDuration}}, {{api|C_Spell.GetSpellChargeDuration|GetSpellChargeDuration}}, {{api|C_ActionBar.GetActionChargeDuration|GetActionChargeDuration}}.
{{text|blizz|Duration Objects}}
*{{api|t=sc|DurationObject|Duration}} objects that measure a zero-span are now considered fully elapsed.
{{text|blizz|Auras}}
*The <code>isHelpful</code>, <code>isHarmful</code>, <code>isRaid</code>, <code>isNameplateOnly</code>, and <code>isFromPlayerOrPlayerPet</code> booleans on aura data tables are no longer secret.
{{text|blizz|Transmog}}
*Added [https://www.townlong-yak.com/framexml/12.0.7/Blizzard_RestrictedAddOnEnvironment/RestrictedEnvironment.lua#216 GetTransmogOutfitIndex] to the restricted environment. Values returned from this can be used with the new [[MACRO outfit|/outfit]] slash command.
{{text|blizz|Lua Documentation}}
*Added a new Predicates table to out Lua API documentation, which will provide a description of the restrictions on each API.
{{text|blizz|Misc.}}
*The {{api|Ambiguate}} function now accepts secrets from addons.
*Added a {{api|t=w|Cooldown:SetCountdownMillisecondsThreshold(seconds)}} API. When a cooldown frame is rendering a time below this number of seconds, it will be displayed as a decimal value with one decimal place (e.g. "8.7").
*String formatting APIs no longer honor field width modifiers for secret string values (e.g. the {{api.inline|"%.5s"}} format will no longer truncate a secret string).
*The {{api|UnitSpellTargetName}} API now only returns names for player units.
{{text|blizz|Bug fixes}}
The {{api|C_EncounterEvents.GetEventSound}} API no longer errors when called.
</details>
<details open>
{{apisummary.header|Coming in upcoming 12.0.5 PTRs}}
{{text|blizz|Misc.}}
*The {{api|UnitTokenFromGUID}} API (and various others) will no longer return arena, nameplate, boss, party, raid, or target-of-target unit tokens when unit identities are secret.
*[[UnitToken#UnitTokenNamePlate|UnitTokenNamePlate]] APIs will no longer accept party, raid, or target-of-target unit tokens.
*Addon execution throttles will no longer apply while the {{api|t=e|PLAYER_LOGOUT}} and {{api|t=e|ADDONS_UNLOADING}} events are being processed.
</details>
<details open>
{{apisummary.header|Future Plans}}
<blockquote {{apisummary.blizzquote}}>
While we have a variety of plans for future patches (12.0.7 and beyond), including many more quality-of-life fixes for addon developers, we wanted to take a moment to talk about one area in particular that we are putting a lot of thought into: Auras (particularly of the Private variety).
We created the Private Aura system back in 10.1 as a means to prevent addons from automating certain very specific fight mechanics. In some ways Private Auras can be viewed as the beginning of our experimentation with adjusting addon capabilities, and while they certainly had their issues, for the most part they served their purpose (albeit in a rather heavy-handed way). When we started developing the Secret Value system, we had hoped (planned even) to be able to essentially retire the Private Aura system and replace it with just secrets.
Unfortunately, as Midnight Alpha & Beta progressed it became clear that relying on Secret Values alone was not going to be enough to prevent addon automation involving auras. And so, we ended up having to go in almost the exact opposite direction: we made MOST encounter debuffs private auras rather than just a select few. While this approach gave us the security we needed for Midnight Season 1, it also came with some significant downsides. Our own private aura displays don't currently have full parity with normal auras, and they aren’t supported in nameplates. On top of that they also require our encounter designers to be very diligent about flagging almost every encounter debuff as private, which is cumbersome and very easy to get wrong.
All this is to say that we are not happy with the current state of auras as they pertain to addons, and we are planning to make some large changes to them. We don't have a hard target yet for when this rework will happen, but just to ease your minds a little it definitely will NOT be in 12.0.5 or 12.0.7. What shape this new aura system will take is also nowhere near decided yet so we won't have any specifics for a while yet, but the overarching goals can be summed up as:
* Auras need to be more secure than they currently are (with less upkeep for designers).
* Auras still need to be customizable and displayable by addons.
* And then as a bonus goal we would like auras to be more performant for addons.
We will be consulting with addon developers as we start to plan out work on this new system, so don't worry about this being dropped on you out of the blue. We just wanted to give you an idea of where our heads are at, so it doesn't come as a surprise later.
Oh and just to make Meo happy, Jar Jar would like to say: ''Wesa will have mooie tings to share berry soon!''

|body=Since the launch of Midnight, we’ve continued to iterate on the addon-related changes introduced in the Midnight pre-patch. In the 12.1 Curse of Ula’tek update, we are pleased to be taking the next major step in that work. This work reflects the insights and feedback shared by our community, with a focus on auras, commonly referred to by players as buffs and debuffs.
These changes focus on preventing auras (whether on the player, enemies, or party and raid members) from leaking important combat information that can be used for combat automation. At the same time, we want addons to continue being able to show auras in a variety of custom ways.
To support that goal, Curse of Ula’tek will introduce new APIs that allow addons to display filtered sets of auras in customized ways, without exposing the underlying aura information that could be used for automation. Addons that currently display auras will need to be updated to support these new APIs, and we’ll be working directly with addon authors throughout the Curse of Ula’tek PTR to help them adapt to these changes and gather feedback during testing.}}

===2026-06-18===
[https://discord.com/channels/327414731654692866/1517308873093152768 {{apisummary.title|Midnight 12.1.0 PTR Changes 1}}] (Build 68209)
<blockquote {{apisummary.blizzquote}}>
Hello again from the World of Warcraft UI Engineering team! Today we’d like to talk about a significant set of Aura-related changes coming in 12.1. Most of these changes will be available when PTR launches, with the remaining pieces rolling out over the following few weeks. 
{{apisummary.heading|Why Auras?}}
Since the Addon Disarmament project went live with Midnight, Auras (aka buffs and debuffs) have consistently been one of the weakest areas for addon security, with numerous exploits discovered both before launch and since then. The core issue is that, in many cases, simply knowing that any aura is present on a unit (whether it be the player, an enemy, or a raid/party member) is enough to determine that some important combat event has occurred. Aura filters are vital for many legitimate addon use cases, but they also make this problem harder to contain by allowing even more ways to tell if “special aura X” is on a unit, even if the unit has multiple auras on them. 
Up until now, our solution to this has been to lean on Private Auras. Unfortunately, Private Auras come with several downsides: they are invisible to addons, which prevents customization; they are not supported in every context, such as nameplates; and setting them up across every encounter adds significant setup work for our designers. Secret values were created specifically to protect against cases like this, providing passive protection by default. 
{{apisummary.heading|What is changing?}}
We’ll get to the changes to existing APIs shortly, but first, we’d like to introduce a couple of new constructs we are adding to Lua, along with two new object types (Aura Containers and Aura Buttons).
{{apisummary.heading|New Tech: Private Script Objects & The Forbidden Partition}}
Private Script Objects are a new construct that lets us split the Lua representation of a script object across multiple Lua tables, or partitions. One of these partitions we call the Forbidden Partition, because it is inaccessible to addons. The Forbidden Partition can contain any kind of value, from mixins to key/value pairs, functions, script handlers, and child objects. This allows us to effectively hide portions of the object from addon code even when the object itself isn’t in the secure environment. 
{{apisummary.heading|New Tech: Forbidden Aspects}}
Forbidden Aspects are another new construct that works alongside Private Script Objects. Forbidden Aspects are similar in concept to the Secret Aspects we introduced in Midnight, but instead of causing certain object APIs to return secrets, they prevent addons from using certain functionality entirely. Where Secret Aspects obfuscate data, Forbidden Aspects restrict what addons are allowed to do with an object. 
There are several Forbidden Aspects being added (details are in the docs), but let’s use the UntrustedScriptExecution Forbidden Aspect as an example. When a frame has the UntrustedScriptExecution Forbidden Aspect applied to it, any script binding handlers set on it (e.g. OnShow, OnLoad, OnSizeChanged) will not be run unless that handler lives in the object’s Forbidden Partition and execution is untainted. In other words, addons cannot install their own script bindings on the object, but our code can.
{{apisummary.heading|New Object Types: Aura Containers & Aura Buttons}}
Aura Containers and Aura Buttons are new Lua object types that allow addons to display auras in custom ways. Here’s a small example showing how they can be used:
<syntaxhighlight lang="lua">
local container = CreateFrame("AuraContainer", nil, UIParent, "CustomAuraContainerTemplate");
container:SetSize(1, 1);
container:SetPoint("CENTER");
container:SetUnit("target");
container:AddAuraFilter("HELPFUL", { maxFrameCount = 5 });
for i = 1, 5 do
	local auraButton = CreateFrame("AuraButton", nil, container, "CustomAuraButtonTemplate");
	auraButton:SetSize(40, 40);
	auraButton:SetPoint("TOPLEFT", container, "TOPLEFT", (i - 1) * 42, 0);
	auraButton.Icon = auraButton:CreateTexture(nil, "OVERLAY");
	auraButton.Icon:SetAllPoints(auraButton);
	auraButton:SetIcon(auraButton.Icon);
	auraButton.Text = auraButton:CreateFontString(nil, "ARTWORK", "GameFontNormal");
	auraButton.Text:SetPoint("TOP", auraButton, "BOTTOM", 0, -5);
	auraButton:SetDurationText(auraButton.Text);
	container:AddAuraFrame(auraButton);
end
</syntaxhighlight>
In the example above, we create an Aura Container, specify that it should track the first 5 helpful auras on the player’s target, and then add 5 Aura Buttons to it. For each Aura Button, we create a texture for the icon and a font string for the duration. The APIs shown here on the Aura Button are just a sample of the APIs provided (full details will be in the docs), but this should give you a sense of what is possible. Note that addon code still has a great deal of control over how the auras are presented, but it doesn’t interact with the underlying aura data at all. This separation is important for security, but it should also make custom aura displays easier to build and more performant. Aura Containers handle the tracking, filtering, and updating of aura assignments internally, so addons can focus more on presentation and less on repeatedly querying, diffing, and refreshing aura state themselves.
{{apisummary.heading|Why Are Aura Containers Safer?}}
To answer that, let’s go back to Private Script Objects and Forbidden Aspects again. Aura Buttons and Aura Containers both have Forbidden Aspects applied to them on creation. When an Aura Button is added to an Aura Container using the {{tlygo|build=ptr|CustomAuraContainerInboundMixin:AddAuraFrame|AddAuraFrame}} API, it is added to the Forbidden Partition of that Aura Container. This means addon code cannot install script handlers on Aura Buttons to be notified when they show or hide. It also cannot hook functions called on the Aura Button’s mixins or register events on those buttons. While addons can still hold references to those individual Aura Buttons, calling certain APIs on them will be disallowed, and they cannot run logic based on whether those buttons are shown, because IsShown and similar APIs return secrets.
{{apisummary.heading|Which current APIs are changing?}}
The main change to existing APIs is that, when auras are secret (during combat, encounters, M+, and PvP matches), all of the UnitAura APIs will now either return full secrets or nil when called by addons. That means that APIs like {{api|C_UnitAuras.GetUnitAuras|GetUnitAuras}} and {{api|C_UnitAuras.GetUnitAuraInstanceIDs|GetUnitAuraInstanceIDs}} will return a secret vector, meaning addon code will not be able to determine how many auras it contains or iterate through it for display. Auras we explicitly flag as non-secret will still be returned as non-secret by UnitAura APIs, however.
{{apisummary.heading|Is all this in place in PTR Week 1?}}
No, several pieces of this are not currently implemented in the first PTR build but will be coming over the next few weeks. The biggest pieces not in place yet are the changes to the UnitAura APIs. Some Aura Button protections are also not yet in place: their script handlers are protected, but script handlers on their child frames are not, and event registration is still currently allowed. Those protections, along with additional safeguards, will arrive over the next few weeks. In the meantime, though, feel free to start experimenting!
As always, we are actively seeking your feedback and will be monitoring the ⁠[https://discord.com/channels/327414731654692866/1376602198687092857 author-wishlist] channel, so please share feedback, bugs, and any potential exploits there. Thanks as always for helping us test and improve this system!
DISCLAIMER: These notes are for addon authors and as such are focused specifically on addon-facing API and security changes only. Changes planned for other parts of the game (UI or otherwise) are not included here.
</blockquote>
{{apisummary.heading|Interface Texture Filenames}}
Starting in 12.1, new interface texture filenames will no longer be published to the ManifestInterfaceData DB, and as a result will not be available via <code>exportinterfacefiles art</code>. '''Existing filenames will remain in the DB.''' You may notice that a few entries are still added in 12.1 and over the next few patches, but this is due to those assets already having been added prior to this change being made. We are making this change to prevent leaks caused by texture names containing hints about future content. We understand that this is going to be a somewhat disruptive change for some addon developers, so please let us know your largest pain points and we'll try to make accommodations where possible.
{{apisummary.heading|Other changes in 12.1 PTR 1}}
* We now support showing SVG textures in our UI. They can be used on regular textures (e.g. {{api.inline|file{{=}}"Path/To/Texture.svg"}}) or with a new {{api|t=o|VectorGraphics}} object type, which renders them at higher quality.
** Note that the VectorGraphics objects don't currently support all of the APIs on regular Textures (rotation, masking, tex coords, etc.)
* Load-on-Demand addons can now specify that specific files in the TOC should load on startup through a new per-file <code>[Bootstrap]</code> directive.
** This still requires that the addon be enabled in order for these files to load.
* {{tlygo|build=ptr|UIParent.lua}} has been heavily refactored, with all of the code that previously handled loading LoD addons moved into the addons themselves, taking advantage of the new <code>[Bootstrap]</code> directive.
* Added a new API {{api|t=w|Frame:SetOnUpdateMode(mode)}}, which lets you specify when the <code>OnUpdate</code> script on a frame should run.
* The options are <code>Disabled</code>, <code>RunWhenVisible</code> (default), <code>RunWhenVisibleOnce</code>, <code>RunOnce</code>, and <code>RunAlways</code>
* A new system has been added called the Roleset System, which allows you to tag a frame as being part of a "roleset". You can then use the new {{api|C_Roleset.ApplyRolesetFilters}} to specify which rolesets are currently active.
** Frames in an inactive roleset will never be shown, regardless of their shown state. See {{tlygo|build=ptr|Blizzard_UIModeManager.lua}} for more details and examples.
* Radial masking support has been added to textures and status bars, allowing them to have a radial mask applied to them without the need for hacky uses of cooldowns. Example usage on a texture:
<syntaxhighlight lang="lua">
texture:SetRadialProgressBarPercent(0.5);
texture:SetRadialProgressBarStartOffset(0.25);
texture:SetRadialProgressBarEndOffset(0.75);
texture:SetRadialProgressBarReverse(true);
texture:SetRadialProgressBarFeather(0.125);
</syntaxhighlight>
* KeyValues can now specify that their value should be pulled directly from the private addon table. Example usage: {{api.inline|lang=xml|<KeyValue key{{=}}"myKey" type{{=}}"local"/>}}
* Mixins can now be added on an object using a new {{api.inline|lang=xml|<Mixins>}} element.
** Using this element allows you to use the <code>source="local"</code> specifier to indicate the mixin lives in the private addon table.
** Mixins added on an object (either through the Mixins element or the regular <code>mixin="myMixin"</code> attribute) can also now be nested within tables.
Example usage:
<syntaxhighlight lang="lua">
local _addonName, addonTbl = ...;
local CustomFrameMixin = {};
addonTbl.CustomFrameMixin = CustomFrameMixin;
local NestedMixin = {};
addonTbl.Mixins = {};
addonTbl.Mixins.NestedMixin = NestedMixin;
</syntaxhighlight>
<syntaxhighlight lang="xml">
<Frame name="TestFrame">
    <Mixins>
        <Mixin key="CustomFrameMixin" source="local"/>
        <Mixin key="Mixins.NestedMixin" source="local"/>
    </Mixins>
</Frame>
</syntaxhighlight>

{{apisummary.heading|Coming in 12.1.0 PTR 4}}
This week brings some major changes to {{api|t=i|AuraContainer}}s and {{api|t=i|AuraButton}}s.
* AuraContainers now handle the creation and anchoring of all AuraButtons inside of them entirely on their own.
** Addons no longer create AuraButtons directly. The {{tlygo|build=68412|CustomAuraContainerSharedMixin:AddAuraFrame|AddAuraFrame}} API has been removed.
* Added a new construct to AuraContainers: ''AuraGroups''. Broadly speaking, you can think of an AuraGroup as a dynamic, self-managing collection of auras within an AuraContainer.
** AuraContainers can have multiple AuraGroups, each with their own filters and settings.
** Auras from each group are anchored sequentially in the order the groups were added.
* Addons add AuraGroups to AuraContainers using a new API {{tlygo|CustomAuraContainerSharedMixin:AddAuraGroup|AddAuraGroup(groupKey, filterString, options)}}.
** The <code>groupKey</code> param is an arbitrary addon-defined string used to access the group after creation.
** The <code>filterString</code> param is a standard aura filter string as used today (e.g. {{api.inline|"HELPFUL<nowiki>|</nowiki>RAID"}}).
*** The <code>options</code> param is a table that can contain a number of optional settings.
**** <code>maxFrameCount</code>: The maximum number of aura frames to show in this group
**** <code>sortMethod</code> and <code>sortDirection</code>: Used to control how auras in this group are sorted (see new enum [https://github.com/Gethe/wow-ui-source/blob/12.1.0/Interface/AddOns/Blizzard_AuraContainer/Blizzard_AuraContainerShared.lua#L40 AuraContainerSortMethod] for choices).
**** <code>initializeFrame</code>: A callback function that is called for each AuraButton created.
**** <code>templateNames</code>: A list of xml templates to apply to each AuraButton (in addition to {{tlygo|CustomAuraButtonTemplate}}).

===2026-09-03===
[https://discord.com/channels/327414731654692866/1545113129736871966 {{apisummary.title|Midnight 12.1.5 PTR Changes 1}}] (Build 69594)
{{apisummary.header|Coming in 12.1.5 PTR 1}}
{{apisummary.heading|Aura Pandemic Animations}}
* [[INTRINSIC_AuraButton|CustomAuraButton]] now supports Pandemic-triggered animations via new APIs.
** Three Pandemic triggers are supported: '''Enter''' and '''Active''' (both triggered when entering Pandemic), and '''Leave''' (triggered when leaving Pandemic).
*** '''Enter''' is intended for one-shot animations, while Active is intended for looping animations.
** Each trigger type has a set of APIs for adding and removing individual animation groups, or clearing all animation groups for that trigger.
** Two new [[Secret_Values#Forbidden_aspects|forbidden aspects]] were added to support this:
*** <code>QueryAnimationProgress</code>: prevents querying the progress of an animation or whether it is running.
*** <code>AddAnimations</code>: prevents animations from being added or reparented.
** Animations used by Pandemic triggers also gain the existing <code>ChangeAnimationTarget</code> forbidden aspect.
<syntaxhighlight lang="lua">
local glow = auraButton:CreateTexture(nil, "OVERLAY");
glow:SetColorTexture(1, 0, 0);
glow:SetAllPoints(auraButton);
local animGroup = glow:CreateAnimationGroup();
animGroup:SetLooping("BOUNCE");
local animAlpha = animGroup:CreateAnimation("Alpha");
animAlpha:SetFromAlpha(0);
animAlpha:SetToAlpha(1);
animAlpha:SetDuration(0.5);
auraButton:AddPandemicActiveAnimation(animGroup);
</syntaxhighlight>
{{apisummary.heading|Aura Containers}}
* <code>CustomAuraButton</code> now supports showing the aura's caster in a fontstring via the new {{api|t=w|AuraButton_SetCasterName|SetCasterName}} API.
* {{api|t=w|AuraButton_AddDispelTypeTexture|AddDispelTypeTexture}} and {{api|t=w|AuraButton_AddPandemicRegion|AddPandemicRegion}} no longer return an index. The corresponding {{api|t=w|AuraButton_RemoveDispelTypeTexture|RemoveDispelTypeTexture}} and {{api|t=w|AuraButton_RemovePandemicRegion|RemovePandemicRegion}} APIs now take a region reference instead of an index.
* <code>AddDispelTypeTexture</code> and <code>AddPandemicRegion</code> now raise an error if the same region is added multiple times.
* Aura tooltips now support displaying the aura's caster, colorized by reaction or class color. This functionality is controlled by the new {{apitooltip|type=cvar|name=tooltipShowAuraCasterNames|default=0|scope=Account|cat=4|desc=Show caster unit names in tooltips for unit auras.}} CVar.
* New [[INTRINSIC_AuraContainer|CustomAuraContainer]] APIs allow individual items to be '''disabled''' via {{api|t=w|AuraContainer_SetAuraGroupEnabled|SetAuraGroupEnabled}}, {{api|t=w|AuraContainer_SetAuraSlotEnabled|SetAuraSlotEnabled}}, and {{api|t=w|AuraContainer_SetItemEnchantmentEnabled|SetItemEnchantmentEnabled}}.
* <code>CustomAuraButton</code> now supports a <code>minApplications</code> option in {{api|t=w|AuraButton_SetApplicationBar|SetApplicationBar}}, which prevents the application bar from being shown unless the number of applications exceeds the specified value.
* A new {{api|t=w|AuraContainer_SetEditModePreviewEnabled|SetEditModePreviewEnabled}} API has been added to <code>CustomAuraContainer</code> to control whether preview auras are shown while the player is in Edit Mode.
* <code>CustomAuraContainer</code> now correctly refreshes in response to {{api|t=e|UNIT_FLAGS}} and {{api|t=e|UNIT_FACTION}} events.
{{apisummary.heading|AddOn Security}}
* The {{api|t=w|Cooldown_SetCooldown|SetCooldown}} and {{api|t=w|Cooldown_Clear|Clear}} cooldown APIs can no longer be called from tainted code when the cooldown frame itself is protected.
* Castbar IDs are now '''unique per unit token''', preventing addons from using them to compare units.
** '''Note:''' Unit token casing matters when querying castbar IDs; a {{api|UnitCastingInfo}} query for {{api.inline|"PLAYER"}} returns a different castbar ID than one for {{api.inline|"player"}}. Events always use '''lowercase unit tokens'''.
{{apisummary.heading|Script Object APIs}}
* A new {{api|t=sc|TimedSignalMap}} script object has been added for scheduling a '''single callback''' which is invoked with '''user-defined keys''' at specified times.
** Keys can be dynamically '''rescheduled without requiring cancellation''', unlike timer objects, making <code>TimedSignalMap</code> useful as a lower-level scheduling primitive.
** The {{tlygo|TimerUtil.CreateTimedSignalCallbackMap|CreateTimedSignalCallbackMap}} API (in <code>TimerUtil</code>) is a convenience wrapper that generates keys and associates each key with a callback.
* A new {{api|CreateFrameWithOptions}} API has been added, which takes a table with named options as its only parameter.
** The options currently supported mirror those accepted by {{api|CreateFrame}}: <code>frameType</code> (required), <code>name</code>, <code>parent</code>, <code>inherits</code> (as an ''array'' of template names), <code>id</code>, and <code>hidden</code> (new; hides the frame by default).
* Added a new <code>roundLayoutToNearestPixel</code> XML attribute and {{api|t=w|ScriptRegion_SetRoundLayoutToNearestPixel|SetRoundLayoutToNearestPixel}} API to all Regions. When enabled, layout changes are automatically '''rounded to the nearest pixel'''.
** These provide a '''native-code replacement''' for the Lua <code>PixelUtil</code> functions; {{tlygo|PixelUtil.SetRoundLayoutToNearestPixelRecursively}} can be used to apply the setting to a region and all its children.
{{apisummary.heading|Lua Utility Functions}}
* A suite of math, string, and table utility functions has been added. Some were previously implemented in Lua and have now been moved to native code; aliases for the existing names have been retained to prevent addon breakage.
** Math functions: {{api|math.clamp}}, {{api|math.saturate}}, {{api|math.round}}, {{api|math.lerp}}, {{api|math.normalize}}, {{api|math.sign}}, {{api|math.remap}}, {{api|math.wrap}}, {{api|math.isfinite}}, {{api|math.isnan}}, and {{api|math.isinf}}.
** String functions: {{api|string.contains}}, {{api|string.ltrim}}, {{api|string.rtrim}}, {{api|string.startswith}}, and {{api|string.endswith}}.
** Table functions: {{api|table.isempty}}, {{api|table.contains}}, {{api|table.indexof}}, {{api|table.removeunordered}}, {{api|table.removevalue}}, {{api|table.keys}}, and {{api|table.values}}.
{{apisummary.heading|Deprecations}}
* The following deprecated addons have been removed. Update your code to no longer use the deprecated APIs they contained:

{{apisummary.heading|Miscellaneous}}
* A new {{apisystem|WeatherScript|C_Weather}} namespace blows in, providing access to current weather conditions and an event when they change.
* A new {{apisystem|Intl|C_Intl}} namespace provides functions for working with Unicode and internationalization.
* The spell ID line shown in spell tooltips via the {{apitooltip|type=cvar|name=tooltipShowAuraSpellIDs|default=0|cat=4|desc=Show spell IDs in tooltips for unit auras.}} CVar is now correctly localized, and no longer uses the same color as spell description text.
* Mythic+ enemy forces lines in tooltips now use a distinct line type: <code>Enum.TooltipDataLineType.UnitCriteriaProgress</code>.
* Pinging a macro containing a <code>#showtooltip</code> line now pings the corresponding spell.
* Fixed an issue that could prevent duration objects from rendering for long-duration auras in some cases.
* Fixed a performance issue with the {{api|EnumerateFrames}} API.
* Fixed an issue where calling {{api|t=w|Frame_Hide|Hide}} directly on a panel, rather than {{tlygo|HideUIPanel}}, could prevent the Game Menu from being shown.

===2026-09-16===
[https://discord.com/channels/327414731654692866/1549542072816635984 {{apisummary.title|Midnight 12.1.5 PTR Changes 2}}] (Build 69848)
{{apisummary.header|Coming in 12.1.5 PTR 2}}
{{apisummary.heading|Aura Containers}}
* Fixed an issue where using <code>includeSpellIDs</code> to show only specific never-secret auras, such as Sated, could also allow unrelated auras through.
* Fixed an issue where the <code>ProcessAura</code> policy did not correctly filter out auras that returned <code>ProcessAuraType.None</code>.
* {{api|t=i|AuraButton|CustomAuraButton}} now supports two additional animation triggers.
** '''Shown''' animations play the first time an aura becomes visible on the button, and stop when the aura is no longer shown, using {{tlygo|CustomAuraButtonSharedMixin:AddAuraShownAnimation|AddAuraShownAnimation}}.
** '''Assigned''' animations play whenever a new aura is assigned to the button, independent of visibility, using {{tlygo|CustomAuraButtonSharedMixin:AddAuraAssignedAnimation|AddAuraAssignedAnimation}}.
* <code>CustomAuraButton</code> animations now apply [[secret aspects]] for <code>VertexColor</code> and <code>TexCoords</code> to target objects.
{{apisummary.heading|AddOn Security}}
* The <code>sourceGUID</code> field returned by Damage Meter APIs is now secret when the unit's identity is secret.
* Added a new [https://github.com/Gethe/wow-ui-source/blob/12.1.5/Interface/AddOns/Blizzard_UnitFrame/Shared/UnitFrameUtil.lua UnitFrameUtil] Lua library, focused on providing addon-safe APIs for unit frame addons to set textures based on now-secret APIs.
** The first new API is [https://github.com/Gethe/wow-ui-source/blob/12.1.5/Interface/AddOns/Blizzard_UnitFrame/Shared/UnitFrameUtil.lua#L145 UpdateUnitPvPIndicator], with more APIs coming in future PTR builds.
* [[C_Intl]] functions now accept '''secret string arguments from tainted code'''.
** The {{api|C_Intl.Transliterate}} API does not allow <code>Null</code> or <code>Remove</code> transliterators for secret text from tainted code.
* The {{api|C_Intl.FindStringMatches}} and {{api|C_Intl.FindBreaks}} APIs now return '''1-based indices'''.
* Fixed a bug where RaidWarning frames could retain secret aspects on their fontstrings after being returned to the pool.
* Addons now get an '''additional one-frame window''' to adjust the hitbox of an enemy nameplate if a {{api|t=e|UNIT_CLASSIFICATION_CHANGED}} event arrives after the nameplate was already created.
{{apisummary.heading|Miscellaneous}}
* A new optional <code>throttleSeconds</code> parameter was added to the {{api|C_UnitAuras.AddAuraSound}} API, allowing addons to specify '''how often the sound should be allowed to play'''.
* Fixed an issue that could cause some APIs, like tostring and dumpobject, to crash when passed secret objects.
* Chat tabs no longer use {{tlygo|UIFrameFlash}} for their flash animations, hopefully '''reducing chat tab taint issues''' caused by unrelated systems.
* {{api|C_ClassColor.GetClassColor}} now accepts an '''optional tint color''', which is multiplied by the class color before it is returned.
* {{api|GetPlayerInfoByGUID}} now also returns the unit's level, if known.
* The following CVars, removed in Midnight, have been restored: {{apitooltip|type=cvar|name=nameplateMotionSpeed|default=0.025000|cat=4|desc=Controls the rate at which nameplate animates into their target locations [0.0-1.0]}}, {{apitooltip|type=cvar|name=nameplateBottomInset|default=0.100000|cat=4|desc=The inset from the bottom (in screen percent) that nameplates are clamped to.}}, and {{apitooltip|type=cvar|name=nameplateTopInset|default=0.080000|cat=4|desc=The inset from the top (in screen percent) that nameplates are clamped to.}}.
* {{api|t=o|RadialProgress}} animations can now be created from XML.
* Fixed a texture masking bug affecting frames using more than one mask texture with different wrap modes.
* Fixed a bug that could cause the right-click unit menu to incorrectly show battle-pet options for a distant player. This is '''pending a hotfix to 12.1.0''' as well.
